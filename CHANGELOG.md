# Changelog

Notable changes to `isaac-epics`. Versions follow [semantic versioning](https://semver.org);
while the major version is 0 the wire protocol and configuration format may
still change, and `PROTOCOL_VERSION` is what a running pair actually agrees on.

## 0.1.0 — unreleased

First release. Verified end to end on APS hardware (Sentosa, Isaac Sim 6.2.0,
stock Python 3.9): a stock `bp.scan` drives a stock ophyd `EpicsMotor` over
Channel Access into the adapter, over the HTTP tick, into PhysX, and the
measured joint position returns the same way, with no twin-aware code in the
scan. Worst error on a 5-point scan was 17 µm.

### The twin as the IOC

- An Isaac Sim articulation is served as ordinary EPICS **motor records**, so
  existing scan code, ophyd device definitions and Phoebus screens drive it
  unmodified. All 153 record fields are present; the behavioural ones are
  live. See `docs/motor-record.md` for which is which.
- Motion is a trapezoidal profile generated by the adapter from `.VELO` and
  `.ACCL`, so those fields do something and a move passes through the
  intermediate configurations a collision would occur in.
- Soft limits, backlash, retries, `.DMOV`/`.MOVN`, `.MSTA`, `.LVIO` and
  dial/user conversion are implemented as a pure state machine, testable
  without a Channel Access stack or a GPU.
- **Simulation time drives the trajectory; wall time drives staleness only.**
  A move therefore cannot complete while the simulation is paused, and a
  frozen readback sitting inside the deadband is never mistaken for a settled
  move.
- When frames stop, readbacks go `INVALID`, `.MSTA` raises `PROBLEM` and
  `COMM_ERR`, and `.DMOV` is withheld, so a waiting scan blocks visibly
  instead of being handed fabricated telemetry.
- Channel Access binds to loopback and the PV prefix defaults to `SIM:TWIN:`.
  Serving simulated motors beyond the host is a deliberate act and is logged
  as one.

### Mirror mode

- A real beamline's readbacks can drive the articulation, read-only. The
  module cannot write to a PV and a test enforces that statically. Works
  against live PVs; **not yet run against a real beamline.**

### Models and configuration

- One JSON file per instrument, normally produced by `--emit-config` rather
  than written by hand. Engineering units are converted in exactly one place.
- The configuration is checked against the live articulation on the first
  frame — joint names matching nothing, soft limits outside the physical
  joint, a stage at the wrong scale — and the verdict is published on `CFGOK`
  and `CFGMSG`. Findings are reported, not fatal.
- Tools to convert real vendor CAD to riggable USD and author a physics
  articulation onto it in a separate layer, so re-converting the geometry
  cannot destroy the rigging.
- A joint prim may declare `epics:motorPV`, the PV it expects to be driven
  by. `--emit-config` then takes motor names and prefix from the model, so
  the asset and the configuration agree by construction.

### Interacting with it

- `isaac-epics-console`: an IPython console with Bluesky's SPEC-style magics
  (`%mov`, `%movr`, `%wa`, `%ct`) bound to the configured axes. No new command
  language is invented.
- `isaac-epics-tick --install <dir>` writes out the stdlib-only file that runs
  inside Isaac Sim. It ships inside the wheel, so a pip install is enough to
  obtain both halves of the link, and the emitted file always matches the
  adapter that emitted it.
- `isaac-epics-ioc --list-pvs` prints every PV without starting a server.

### Not included

- **Commanding real hardware from the twin.** A controls-safety and
  access-security question, not a software one, and deliberately absent.
